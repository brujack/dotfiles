| `config/profiles.sh` silently mis-resolves under bash 3.2 — no version guard | The file header says "requires bash 5+" and nothing enforces it. Under `/bin/bash` 3.2 (macOS system bash) `declare -A` errors, the array literal collapses to an indexed array, and a string subscript resolves to **element 0 or the last element** rather than failing. Measured 2026-08-18 on the Studio, hostname `studio`: master `PROFILE_MAP[studio]` -> `wsl2_workstation` (want `mac_workstation`), and post-#223 `PROFILE_LEGACY[studio]` -> `CRUNCHER` (want `STUDIO`), so `detect_env` would set `readonly CRUNCHER=1` — and `readonly` inside a bash function is global and irreparable for the process. **Not fail-closed**: a security-review pass described the new table as returning empty under 3.2; it returns a wrong value, same as the old one. Reachable because `setup_env.sh` is `#!/usr/bin/env bash` and `ssh host '<cmd>'`, cron and launchd all get `_PATH_STDPATH`, where `/usr/bin/env bash` finds 3.2 — see `CLAUDE.md`'s actor table. Pre-existing on master and out of scope for #223 under Surgical Changes. Fix is a guard at the top of `config/profiles.sh`: `[[ ${BASH_VERSINFO[0]:-0} -ge 4 ]]` or exit non-zero with the remedy named, so a 3.2 caller fails loudly instead of resolving a different machine's identity. Note the zsh reader is unaffected. |
| `.zprofile` duplicates the rbenv init that `5_general.zsh` now gates by capability | `.zprofile:10-14` runs the same `rbenv init` behind `[[ -n ${WORKSTATION} ]] || [[ -n ${CRUNCHER} ]]` with a hardcoded `/home/linuxbrew/.linuxbrew/bin/rbenv` path, no `_OVERRIDE_*` seam, and no bats test sourcing it for rbenv. After dotfiles#223 the interactive path (`5_general.zsh:77`) asks `HAS_DEVTOOLS` while the login path still asks by hostname, so login and interactive answer the same question two different ways. They agree today — `workstation`/`cruncher` are exactly the two hosts carrying `devtools` — but the next Linux devtools host added to `PROFILE_MAP` gets rbenv interactively and not at login, silently. Found by the T1 code-quality review; out of scope there because `.zprofile` was not in `files_touched`. Fix wants the same seam treatment `5_general.zsh` already has, so a test can drive it. |
| `.zshrc:8,11` is the real owner of gcloud sourcing, duplicated in `5_general.zsh` | `.zshrc` sources `path.zsh.inc` and `completion.zsh.inc` from `/opt/homebrew/share/google-cloud-sdk` with **no hostname guard**, five lines below the `.zshrc.d` loop. `5_general.zsh:129-143` sources the same pair behind a `RATNA`/`LAPTOP`/`STUDIO` guard using the pre-2026-04-30 `Caskroom/google-cloud-sdk` cask token. Measured 2026-08-17 with `hostname` mocked to `reception`: completion ABSENT after the `.zshrc.d` loop, LOADED after `.zshrc:11` — so on ARM the duplicate's guard buys nothing and the earlier "completion absent on three work macs" framing is refuted. `.zshrc` hardcodes `/opt/homebrew`, so it no-ops on Intel and `ratna` is served only by the `5_general` copy. ## Adding a new entry

When a new spec or plan is created, add a row to the All Plans table. Set status to **In Progress** when implementation starts, **Done** when the PR merges. Also add a `> **Status: DONE**` banner at the top of the plan file once complete. Move backlog items to the All Plans table when their spec is written (remove the backlog row).
